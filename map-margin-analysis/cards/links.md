# Links — Project, Contract, Model, Community   (live)

**Source:** table `tblEXAMPLE0000007`; link fields `fldEXAMPLE0000052` (Project → `tblEXAMPLE0000009` 🏗️ Projects and Addresses), `fldEXAMPLE0000053` (Contract → `tblEXAMPLE0000010` 🏗️ Contract), `fldEXAMPLE0000054` (Model Link → `tblEXAMPLE0000011` 📍 Models), `fldEXAMPLE0000055` (Community → `tblEXAMPLE0000012` 📍 Community Name).
**What it is:** where a snapshot gets its identity, its fallback inputs, and its one independent check. Project is linked in every one of the 347 records, Community in 346 of 347, Model in 272, Contract in 241.
**Shape:** Project feeds the label and the identity lookups (job address, community, total SF, customer name). Model feeds the sq-ft and cost-per-sq-ft lookups the cost stack falls back on when no override is typed (cards/cost-stack.md). Contract feeds exactly one lookup — the pre-GST sale price plus change orders (`fldEXAMPLE0000056`) — which drives `⚠️ Revenue Variance vs Contract` (`fldEXAMPLE0000057`) and the `⚠️ Revenue Match?` verdict (`fldEXAMPLE0000058`, $100 tolerance: "Match", "Mismatch: $…", "No contract linked", "Review revenue inputs").
Tripwire: the job address is looked up twice — `fldEXAMPLE0000059` and `fldEXAMPLE0000060` both pull the same Project field. Duplicates, not two data points.
**Hits:** relinking Model moves every Smart sq-ft and cost figure that has no manual override. Relinking Contract flips the revenue-match verdict. Unlinking Project turns the label to "NO DATA" and empties the identity lookups.
**Does not hit:** the Contract's own numbers — the match check reads the contract, it never writes it; fixing a mismatch means editing retail and discount inputs on this table, not the contract. The Monthly Projections link plays no part in anything: it is empty in all 347 records (cards/ghost_monthly-projections-link.md).
